# 運用手順

## 本部WebのPDF・CSV保存

1. 発注書は発行済みの発注から「発注書PDF」、領収書は取引から「再印刷PDF」、返還伝票は返金確定後に「返還伝票PDF」を選ぶ。CSV・一式出力は画面下部の「データ・帳票出力」から作成する。
2. 作成を受け付けると画面下部の「出力履歴」が自動で開く。作成待ち・作成中の記録は自動更新されるため、更新ボタンを連打しない。
3. 「作成完了」になった行の「PDFをダウンロード」「CSVをダウンロード」「一式をダウンロード」を押して保存する。新しいタブや印刷画面を自動で開く動作ではない。
4. すでに作成済みのファイルは、画面下部の「出力履歴」を開いてそのまま保存できる。一式はPDF・CSV等をまとめた `tar.gz` なので、ダウンロード後に展開する。

PDFはA4縦、日本語フォント埋め込みで出力する。領収書・発注書・返還伝票は、宛先と発行者、伝票番号、日本時間の日付、合計金額、明細表、備考、ページ番号を共通の体裁で表示し、複数ページでは表見出しを繰り返す。領収書には保存済みの店内/持ち帰り区分・値引き・税率別税込金額と税額・支払情報、返還伝票には元販売日と元税率別返金額を表示する。発注書の仕入単価は税区分を保存していないため、税込/税抜や0%を推測せず、その旨を注記する。

帳票の名称・価格・税率・発行者は取引時の保存内容を使い、発注書は発行時点のスナップショットを使う。過去の取引や、作成済みPDFを上書きしない。体裁の更新後は、取引の「再印刷PDF」等から新しい出力を作成して保存する。「出力履歴」の古いファイルを再ダウンロードしても新しい体裁には変わらない。未設定の宛名や発行者情報を補完・創作しない。5. 通信エラー時は原因と次の操作を表示し、完了状態の確認を再試行する。サーバー停止中は取得できないため、個人検証環境では起動を確認する。作成エラー・再試行待ちが続く場合はワーカーログとS3/SQS権限を確認する。

## D0 sandbox の配備・復元

単一EC2のD0は [sandbox構成](aws-sandbox.md)、[配備手順](runbook/deploy.md)、[復元手順](runbook/restore.md) を使用する。毎時・起動直後・停止直前のbackupと大阪への複製を、Macからの適用後に受け入れる。今回のVMではAWS操作を行っていない。端末の原イベントと復元点の照合も復元訓練に含める。

## 将来の Tier M 配備（D0対象外）

1. 専用 AWS 検証アカウント、東京リージョン、DNS、ACM 証明書、国内 Bedrock プロファイルの権限・推論先リージョンを確認する。
2. `infra/` を init/validate/plan。イメージは Dockerfile からビルドして ECR 等へ登録する。レビュー済み plan 以外を apply しない。
3. Terraform state は暗号化 S3 と state locking で管理する。`app_database_url` は sensitive だが state に含まれるため state 自体にもアクセス制御が必要。
4. RDS 所有者と `regi_app` を分ける。アプリロールを NOSUPERUSER/NOBYPASSRLS にし、所有者でマイグレーションを一度だけ実行する。アプリタスクへ所有者 URL を渡さない。
5. Cognito は管理者作成のみ、MFA ON。`custom:tenant_id` を管理者が設定し、実際の Cognito subject を staff に関連付ける。任意の JWT custom claim をクライアントから設定できないことを確認する。
6. 回収署名鍵を Secrets Manager に保管し、Terraformの `recovery_signing_secret_arn` を設定する。更新契約は販売者隔離環境のEd25519秘密鍵で発行し、APIには `renewal_public_key` の公開鍵のみ設定する。秘密鍵をソースやコンテナーに埋め込まない。
7. S3 は非公開、暗号化。CloudFront の OAC で Web のみ配信する。帳票は認証 API 経由で取得する。
8. API 2タスク、ワーカー、SQS/DLQ、RDS Multi-AZ を接続。バックアップ35日、PITR、削除保護を確認する。
9. Web の Cognito callback、CORS、ALB の API DNS を実環境へ一致させる。Bedrock の国内プロファイル ARN と対応モデル ARN を IAM の最小権限に照合する。
10. `worker_scopes` に法人・有効スタッフIDを設定する。ワーカーの `DAILY_JOBS=true` は日締め済み日のPython予測とAI日報を生成し、完了記録で重複を避ける。手動予測は `forecast/regi_forecast.py --tenant <UUID> --store <UUID>`。RLSを維持し、実環境で翌日の実行・技術失敗のバックオフ・日本時間の月次枠を検証する。

## 監視・障害対応

- ALB 5xx、ECS 再起動、SQS 滞留/DLQ は Terraform で通知設定を用意。SNS メールの承認を忘れない。
- 店舗別の未送信件数・最終同期・確認待ち会計、AI枠、DB容量、バックアップ失敗、費用のダッシュボードとアラーム閾値をパイロットで校正する。
- POS は72時間・認証/契約のうち最短期限で新規販売を止める。同期失敗時にデータ初期化・再インストールを指示しない。
- 外部決済結果が不明なら端末・決済事業者の明細と照合する。自動成功判定・自動予約解除は行わない。
- 要確認イベントは元ペイロードを保持する。金額不整合を黙って修正した再送やイベントIDの使い回しを行わない。管理者は同期画面/APIで理由付き再検証を行える。既知の履歴価格の承認は可能だが、計算不整合や税率不整合を無条件に通過させない。再検証失敗はトランザクションを戻し、原記録と数量を保持する。
- AI 障害は集計画面へ案内し、技術失敗の枠返還を確認する。反復失敗を自動課金しない。
- SQS 処理失敗はDLQへ移る。権限・対象帳票を確認してから同じ job ID を再投入する。S3キーは法人/ジョブIDで分離する。

## 将来の Tier M 復旧訓練（D0対象外）

1. 復旧開始と最後に同期済みの売上ID・時刻を記録。RPO 5分 / RTO 4時間は設計目標で、保証実測済みと表現しない。
2. RDS の PITR で別インスタンスへ復元し、元 DB を上書きしない。
3. アプリ専用ロール、FORCE RLS、マイグレーション版、税率履歴、売上/返品/在庫台帳、冪等性記録、同期カーソルを照合する。
4. 同じイベントを再送して売上・入荷・返金が増えないことを検査する。
5. S3帳票・SQSを照合し、復元 DB の受領位置より先の端末イベントを再送する。端末側の受領済みイベントも保存されているが、復旧時の再送対象選択は運用者対応。
6. DNS/Secrets切替と既存接続更新を行い、読取・販売・同期を確認。RPO/RTOと不足を記録。

ローカルの `scripts/restore-test.ts` は論理バックアップの復元とマーカー回収を測定するだけで、AWS PITR や本番相当データ量の訓練ではありません。

## 更新・終了

- 検証環境 → パイロット端末 → 全体。旧 Android と API を併存させてイベントの互換性を確認する。
- Room の破壊的 migration は使用しない。未送信・確認待ちが残った状態で認証キャッシュを初期化しない。
- 更新は販売者が隔離環境の秘密鍵で発行した署名付き `proof` を `/v1/settings/renew-contract` へ登録する。公開鍵で法人・契約番号・12か月・税抜240万円・署名期限を照合し、自己申告だけの延長と同一番号の重複更新を拒否する。発行コマンドは README の「更新契約」を参照。
- 終了後30日は閲覧・CSV/帳票出力。90日経過後の業務データ削除とバックアップ全versionの消滅を追跡する。D0のS3はcurrent35日＋noncurrent35日で、versionによって約70日残る場合があり、複製Pending/Failedはさらに長く残り得る。全versionが作成から35日以内に消える保証ではない。法定保管が必要な記録は、契約終了前に利用者がexportして保存する。24か月契約と終了後90日の削除を7年保存の代替と扱わない。
- 削除処理は `scripts/retention.ts`。`MAINTENANCE_DATABASE_URL` を専用所有者接続に設定し、`npx tsx scripts/retention.ts <法人UUID>` で90日経過と件数を dry-run。承認後、同じUUIDで `--execute --confirm=<法人UUID>` を指定する。本番では `ARTIFACT_BUCKET` が必須で、法人プレフィックスの全S3バージョン・削除マーカーを先に削除する。S3失敗時はDBを残す。ローカル試験で期限ガード・削除・RLS/不変トリガー復帰を確認する。
- 削除は保守時間帯に実施する。DB全対象テーブルをロックし、所有者だけが同一トランザクション内で不変制約を一時解除して該当法人を削除し、必ず復帰する。通常APIロールに所有者権限を付与しない。S3とDBは分散トランザクションではないためDB失敗時は同じ承認IDで再確認し、部分削除を記録する。日次スケジューラーへの登録・実S3削除・バックアップ消滅確認は本番接続後の検証対象。
- 端末紛失・破損による未同期データ消失はクラウド RPO の対象外。MDM、物理保護、毎日の同期確認を導入契約で説明する。

## 資格情報と署名鍵の管理

| 種類                         | 保管と責任                                                             | 用途・渡す範囲                                                                 |
| ---------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Cognito管理者のログイン・MFA | 本人の認証環境。パスワードは本人が管理                                 | Hosted UIの本人ログイン。チャット・VM・repositoryへ共有しない                  |
| AWS profile・SSO等の資格     | Macの承認済みAWS資格チェーン。利用者が対象accountを確認                | plan/apply/SSMと復元取得。VMへコピーしない                                     |
| DB owner/app資格・回収署名鍵 | Secrets Managerとhostのroot管理0600ファイル。運用担当が分離を維持      | appにはNOSUPERUSER/NOBYPASSRLS接続だけ。maintenanceと回収署名の秘密は専用経路  |
| Android debug署名            | SDKのローカル検証環境                                                  | 開発用APK。商用配布用署名の代わりにしない                                      |
| Android配布・upload署名鍵    | 作成・保管責任者と復旧手順を配布前に確定。現時点で提供済みとは扱わない | 配布経路が必要とする署名。鍵本文・store passwordはrepositoryやVMへ持ち込まない |
| 更新契約のEd25519秘密鍵      | 販売者の隔離された署名環境。所有者と復旧手順を管理                     | 署名付きproofを発行。APIには公開鍵だけを渡す                                   |

.env・私有tfvars・state・鍵・.contextはコミット対象から除外する。ログやSSM command引数へ秘密本文を入れず、必要な検査は件数・SHA・固定の段階名で記録する。
